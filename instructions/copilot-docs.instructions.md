# .copilot-docs の構成ルール

## 目的

- `.copilot-docs` は、AI エージェントが短時間で全体像と参照先を掴むための一次資料として扱う
- 説明は **結論 → 判断材料 → 詳細** の順で書く
- 重複説明を避け、詳細は他ドキュメントへリンクして分散する
- `operation.md` はユーザも読む前提で、視認性と操作しやすさを優先する

## 共通ルール

- 各ファイルの冒頭に、3 行以内の要約を置く
- 要約の直後に「この資料で分かること」と「関連資料」を置く
- 1 つの見出しでは 1 つの論点だけを扱う
- 長い散文より、表・箇条書き・短い段落を優先する
- 実装コードやログを大量に貼らず、必要なファイル名・責務・入出力だけを書く
- AI が読まなくてよい補足は本文に混ぜず、別見出しに分離する
- 未確定事項は推測で埋めず、`未確定`、`調査中`、`今後追加` のように明示する
- 新しい文書を増やす前に、既存の `index.md`、`architecture.md`、`api.md`、`operation.md` のどこに置くべきかを先に検討する

## AI が読みやすい書き方

- 最初に読むべき情報を上に置き、背景説明は後ろに回す
- 関連するソースコードや設定は、ファイルパスを明記して探しやすくする
- 責務、入力、出力、依存先、影響範囲は表で整理する
- 同じ説明を複数ファイルに重複記載せず、正本となる文書を 1 つ決める
- 文書をまたぐ前提知識が必要な場合は、「先に読む資料」を明記する

## 推奨ファイル構成

### index.md

- 文書一覧ではなく、**読む順番の案内**を主目的にする
- 各文書について「何が分かるか」「いつ読むか」を 1 行で書く
- 変更時は新規文書を追加するだけでなく、読み順と参照関係も更新する

### architecture.md

- 最初にシステム全体像と主要コンポーネントを示す
- モジュールごとに、責務、主な入力、主な出力、依存先、関連ファイルを書く
- 詳細な処理手順より、依存関係と境界を優先して説明する

### api.md

- API や外部契約は、一覧表を先に置いてから個別詳細を書く
- 各項目では、目的、呼び出し元、入力、出力、エラー、副作用を揃えて書く
- 実装順ではなく、利用者が辿りやすい単位で並べる

### operation.md

- ユーザ向け資料として、最初に「何ができるか」を短く示す
- 画面や機能の説明より、**達成したい操作単位**で章を分ける
- 各操作は `目的`、`前提条件`、`手順`、`結果`、`失敗時の確認点` の順で書く
- 手順は必ず順序付きリストで書き、1 ステップ 1 動作にする
- 分岐がある場合は長文で書かず、表やフローチャートで整理する
- 見た目の情報量を増やしすぎる画像より、表、箇条書き、Mermaid を優先する
- 実装都合の内部用語は避け、ユーザが見る名称を優先する

## operation.md の見やすさルール

- 1 セクションの冒頭で、対象読者と達成できることを先に示す
- 手順の前に前提条件をまとめ、途中で前提を差し込まない
- 注意事項は本文に埋め込まず、`注意` や `補足` の見出しに分ける
- 例外ケースは末尾にまとめ、通常操作の流れを中断しない
- Mermaid を使う場合は、本文より分かりやすくなるときだけ使う

## 更新方針

- 文書更新時は、変更箇所だけでなく、参照先との整合性も確認する
- 仕様変更があった場合は、`index.md` から辿れる状態を維持する
- 古い説明を残すより、不要になった記述を削除して文書を短く保つ
