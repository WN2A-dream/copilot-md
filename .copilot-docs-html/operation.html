ユーザが orchestrator を中心に開発タスクを進めるときの操作ガイド。auto_mode や追加指示、再計画の戻り方も含めて現在の流れを示す。

開発タスクの依頼

目的

コード実装・修正を orchestrator に依頼し、必要な再計画を含めて完了まで進める。

手順

  1. Copilot Chat で orchestrator を呼び出す。
  2. 実装したい内容、制約、避けたいことを自然言語で伝える。
  3. orchestrator がショートカット判定を行い、design-only / investigation-only でなければ統一フローへ進む。
  4. splitter がタスク規模を判定し、必要に応じて分割する。
  5. investigator が現状を調査し、planner が plan を提示する。
  6. plan を確認し、ok か、修正指示か、追加指示を返す。
  7. ok の場合、developer が実装し、tester と reviewer が並列で評価する。
  8. テスト失敗・レビュー NG の場合、investigator に戻ってリトライする。
  9. 全サブタスクが ok になると、documenter が .copilot-docs/ を更新し、.copilot-docs-html/ を再生成する。
  10. 最終結果に対して追加指示があれば、orchestrator が interviewer を使って整理し、フローをやり直す。

結果

  • .copilot-work/[task-id]/ に hearing、preferences、調査、plan、開発結果、テスト結果、レビューが残る
  • .copilot-docs/ が更新される
  • .copilot-docs-html/ が再生成され、一覧検索とページ内検索で閲覧できる

auto_mode

目的

1リクエストでタスクを完走させる。ユーザ確認ゲートをスキップし、テスト失敗・レビュー NG 時は自動リトライする。

使い方

タスク依頼時に auto_mode を示すキーワード（例: 「自動で」「一気に」等）を含めると、orchestrator が auto_mode を検出する。

動作の違い

ゲート 通常モード auto_mode
ショートカット判定 design-only / investigation-only を検出 スキップ（即統一フローへ）
plan 確認 ユーザに確認を求める 自動承認
テスト失敗 ユーザに対応を確認 investigator に自動リトライ（MAX_RETRY まで）
レビュー NG ユーザに対応を確認 investigator に自動リトライ（MAX_RETRY まで）
最終確認 ユーザに結果を報告 スキップして documenter へ
MAX_RETRY 超過 — 自動停止

追加指示の返し方

返し方 使う場面 orchestrator の動作
ok 現在の plan / 結果で進めてよい 次の工程へ進む、または終了する
ng（修正） 現在の案に問題がある interviewer で修正意図を整理し、preferences.md を更新して再計画する
追加指示 新しい条件を足したい 追加内容を hearing と preferences に反映して最初から流し直す
追加指示ファイルがある 要件を別ファイルで渡したい ファイルパスを interviewer に渡して読み込ませ、以後の plan に反映する
Interviewer で整理する 指示を会話しながら固めたい interviewer を呼び、十分な情報が集まるまで質問を続ける

ファイルリンク表示

orchestrator は plan 承認の確認時などに、関連ファイルへのマークダウンリンクをチャット上に表示する。ユーザはリンクをクリックしてファイル内容を直接確認できる。

表示されるリンク例:

  • [plan1.md](.copilot-work/{task-id}/plans/plan1.md)
  • [hearing.md](.copilot-work/{task-id}/hearing.md)
  • [investigation.md](.copilot-work/{task-id}/investigation.md)

セットアップタスク

目的

プロジェクトの初期ドキュメントや運用資料を整備する。

手順

  1. orchestrator にセットアップ内容を依頼する。
  2. orchestrator がタスクを正規化し、統一フローで処理する。
  3. investigator が現状を調査し、planner が計画を作成する。
  4. developer が実装し、tester + reviewer が評価する。
  5. documenter が .copilot-docs/ を更新し、.copilot-docs-html/ を再生成する。

結果

  • 共有制御ルート配下の .copilot-docs/ と .copilot-docs-html/ が最新化される

補足

以前はセットアップタスク専用の簡略フロー（developer/reviewer スキップ）があったが、統一フロー化により全タスクが同じフローを通るようになった。
