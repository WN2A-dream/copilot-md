UI デザインガイド

UI を伴う変更で、配色・余白・情報密度・操作感をばらつかせないための最小ガイド。

この資料で分かること

  • UI 実装時に維持すべき共通方針
  • 新しい画面やコンポーネントを追加するときの判断軸

関連資料

  • agents.md — planner / developer / documenter の役割
  • operation.md — 実装依頼から文書更新までの流れ

デザイン方針

  • 既存画面の文脈を壊さず、画面単位ではなくプロダクト全体で一貫した見た目にする
  • 目的の弱い装飾は増やさず、情報構造・視線誘導・操作の分かりやすさを優先する
  • 余白、文字サイズ、強調色、角丸、モーションは画面ごとに変えず、理由があるときだけ更新する
  • デスクトップとモバイルの両方で読みやすく、主要操作に到達しやすい構成にする

基本トークン

項目 基本方針
色 ベース色、強調色、警告色を固定し、同じ意味に同じ色を使う
文字 見出し、本文、補助テキストの階層を 3 段程度に抑える
余白 4 または 8 の倍数で揃え、密度を画面ごとに変えすぎない
角丸 コンテナと入力系で段階を分けつつ、値の種類を増やしすぎない
影 浮かせたい要素だけに限定し、常用しない
モーション 初回表示、展開、並び替えなど意味のある場面だけに使う

レイアウト方針

対象 ルール
ページ全体 主要操作、主コンテンツ、補助情報の順で視線が流れる構成にする
フォーム ラベル、入力、補足、エラーの並びを固定する
一覧 見出し、絞り込み、並び替え、行アクションの位置を揃える
モーダル 破壊的操作を分離し、閉じ方を明確にする
空状態 / エラー 原因、影響、次の行動を 1 画面で分かるようにする

実装ルール

  • planner は UI を含むタスクでこの資料を読み、必要なら計画に更新項目を含める
  • developer は既存 UI とこの資料の両方に合わせて実装し、新しいパターンを勝手に増やさない
  • documenter は UI の方向性が変わったとき、この資料を更新してから HTML 版も再生成する
  • ユーザから UI の嗜好が繰り返し指定された場合は .copilot-work/[task-id]/preferences.md に保持し、必要なら instructions や skills への昇格候補とする

更新が必要なケース

  • 新しい画面種別を追加し、既存のレイアウト規則だけでは判断できないとき
  • 主要な配色、タイポグラフィ、余白、モーションの基準を変更するとき
  • コンポーネントの再利用方針を変えるとき
